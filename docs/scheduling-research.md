# SGLang 原生调度与候选策略调研

调研日期：2026-09-10。本文中的候选策略、收益预期和实验参数都是项目方案，尚未进行实现或真实 GPU 测量。

后续补充：用户已认可本文的候选策略方向，并明确服务器为单卡 A6000，驱动 `580.173.02`、CUDA `12.9`。具体设计与执行顺序分别见[项目设计](project-design.md)和[实现计划](implementation-plan.md)；本文保留源码事实及方案比较。

## 1. 结论与推荐范围

这个方向适合面试项目，但贡献边界需要更新：**SGLang 已经原生支持 HRRN，其核心就是未缓存输入长度与等待老化。**该策略于 2026-09-08 合入上游，不能再把这两个因素的组合本身当作项目新增能力。[HRRN 合入记录][pr-hrrn]

建议保留四个核心原生对照：`fcfs`、`lpm`、`dfs-weight`、`hrrn`。逐步实现四个有明确对照关系的变体：

1. 原始输入短优先：检验只用输入长度能做到什么。
2. 未缓存 token 少优先：检验真实前缀信息带来的收益。
3. 未缓存 token 少优先 + 等待超阈值提升：检验短请求收益与长请求等待的取舍。
4. 估计 prefill 耗时短优先 + 等待超阈值提升：检验更准确的成本估计是否值得其开销。

先完成前三个；第四个依赖远程 GPU 标定。候选数量限制作为同一策略的工程变体单独比较。`lof`、`random` 适合补充实验；`routing-key` 和业务优先级只有在相应负载存在时才值得加入主表。

真正值得讲清楚的问题是：**在相同负载下，哪些请求更快了，哪些请求付出了等待代价，吞吐和缓存复用如何变化，CPU 为此多做了多少工作。**

## 3. 原生策略有哪些

下表列出 `SchedulePolicy` 中的七种排序策略。[策略实现][src-policy]

| 策略 | 实际排序依据 | 适合本项目的作用 |
| --- | --- | --- |
| `fcfs` | 默认保留等待队列顺序 | 核心基线 |
| `lpm` | 匹配前缀 token 数降序，部分队内共享请求暂时降级 | 核心缓存复用基线 |
| `dfs-weight` | 按缓存树子树权重进行深度优先遍历 | 核心缓存聚集基线 |
| `hrrn` | token 等待量除以未缓存输入长度，值大者优先 | 与本项目最接近的核心基线 |
| `lof` | `max_new_tokens` 降序 | 输出长度不同的补充负载 |
| `random` | 随机打乱 | 低成本的补充参照 |
| `routing-key` | 优先选择 `routing_key` 在运行批次中出现较多的请求 | 有路由键和分组负载时补充 |

`lof` 使用调用方设置的输出上限，并不知道真实输出长度。若所有请求的上限相同，这个对照的区分能力很弱。业务优先级是附加机制：当前参数约束允许与 `fcfs`、`lof` 组合；本项目主实验令业务优先级一致，并关闭该附加机制。[优先级参数约束][src-validation]

DFS 的权重来源是匹配到节点的等待请求数量，并沿子树累加；不是按请求预测耗时计算权重。默认实现会遍历缓存树，CPU 开销还与树规模有关。[DFS 实现][src-dfs]

### HRRN 为什么改变项目定位

令 `P` 为调度器累计处理的 prefill token 数，`P_arrival` 为入队时的计数，`R` 为未缓存输入长度。原生 HRRN 依据 `(P - P_arrival) / R` 降序排列；加上常数 1 不改变次序。计数随 prefill 推进，单纯 decode 或经过时间不一定使其增加。[计数更新与入队记录][src-scheduler]

它也沿用队内共享请求的临时降级；相同比值使用 `rid` 打破平局。若一批请求的入队计数相同、期间尚无 prefill 推进，不能假定这一批立刻按最短剩余量排列。[HRRN 排序实现][src-policy]

它与基于秒数的 `1 + 等待时间 / 估计服务时间` 只有在相应吞吐近似稳定等假设下才可类比。上游选用 token 计数还考虑了多 rank 排序一致性；本文不直接移用上游生产集群的性能数字。[HRRN 设计说明][pr-hrrn]

对本项目的推论：应专门比较吞吐波动、decode 较多和突发到达的场景。实际时间老化可能更贴近用户等待，但并不预设优于原生 HRRN。

### LPM 的例子仍然成立

下表只解释排序直觉，`K` 表示 1024 个 token；实际实验使用分词后的长度和服务端测得的命中。

| 请求 | 输入长度 `L` | 可复用前缀 `H` | 剩余量 `R = L - H` |
| --- | ---: | ---: | ---: |
| A | 16K | 12K | 4K |
| B | 2K | 1K | 1K |

LPM 倾向 A，剩余量优先倾向 B。这个例子说明缓存命中总量和剩余工作量是两个目标；要证明 B 的 prefill 更快，仍需 GPU 测量。

## 4. 源码中影响实验解释的细节

### 回退与匹配开销

当前 `lpm`、`hrrn` 在队列长度 **大于 128** 时选择 FCFS 分支；禁用树缓存时，缓存感知策略也会调整为 FCFS。该队列回退分支保留现有队列，没有重新恢复最初到达次序。[回退实现][src-policy]

因此，实验应同时记录配置策略、实际分支、队列长度及回退次数。队列经常超过 128 时，结果不能简单解释为始终运行 LPM 或 HRRN。临时禁用回退的实验必须单独命名，保留原生默认结果。

FCFS 也不意味着完全没有匹配成本：缓存后端支持 `supports_fast_match_prefix()` 且不处于 disaggregated decode 时，缓存无关策略仍会进行队列匹配。这使“仅限制排序候选”与“减少全部匹配调用”成为两个需要分别验证的命题。[调度匹配分支][src-policy] [缓存后端接口][src-unified]

### 排序之后还有批次准入

请求在排序后还要经过 `Req.init_next_round_input()` 和 `PrefillAdder.add_one_req()`；已有分块请求也有自己的续算路径。队首请求可能仍因预算或空间不足而等待。[批次构建调用][src-scheduler]

沿用现有 KV 分配、锁引用和准入流程。新增策略只决定考察顺序，不能把它描述为 decode 抢占策略、完整 SRTF 或硬实时等待保证。

### 排序估计不等于最终执行量

最终可复用长度还受前缀上限等语义影响。例如普通输入匹配通常最多保留到输入长度减一；`logprob` 要求也可能进一步限制匹配。[请求输入准备][src-req]

第一版选择普通文本生成、单一模型和设备侧前缀缓存。成本估计复用引擎的匹配语义，不自行拼接 KV；实际准入阶段仍由原有流程重新确定可复用范围。HiCache 命中涉及搬运，混合注意力模型可能需要补算，这些场景适合后续明确扩展。

### 等待时间需要选对字段

现有 `wait_queue_entry_time` 使用 `time.perf_counter()`，但重新入队时会更新。首次入队和首次准入的统计需在事件发生时记录，不能在请求结束后把可能已改写的字段直接当作首次等待。[时间统计实现][src-time]

`forward_entry_time` 在批次构建附近记录，早于 GPU 实际执行。本项目的“长请求最大等待时间”明确采用首次排队等待，即首次入队到首次准入；GPU 真正开始计算的时刻另由设备侧测量确定。[批次构建调用][src-scheduler]

第一版优先按 `TP=1` 设计，使用同一个单调时钟。若实际服务器需要 `TP>1`，各 rank 独立读取当前时间可能在阈值附近得到不同顺序；需要统一排序决策后再支持该配置。这是计算正确性问题，会扩大“只改排序函数”的实际范围。[上游对多 rank 排序的说明][pr-hrrn]

## 5. 建议实现哪些简单策略

下表名称是本项目建议的标识，**目前不是 SGLang 已支持的参数**。`L` 为原始输入长度，`R` 为本次评估的剩余 prefill token 数，`w` 为已经等待的秒数，`a` 为首次入队顺序，`T_hat` 为估计 prefill 秒数。

下表与候选选择步骤先描述首次等待的新请求。对回退后重新排队的请求，`R` 使用本轮完整待计算输入，`w`、`a` 使用本轮入队记录；首次排队等待指标另行保留，避免把已执行时间算作排队老化。

| 建议标识 | 排序规则 | 开发范围 | 回答的问题 |
| --- | --- | --- | --- |
| `short-input` | `(L, a)` 升序 | 很小；读取已有输入长度 | 不利用缓存信息的短输入优先有多少收益？ |
| `short-remaining` | `(R, a)` 升序 | 小；复用前缀匹配 | 真实命中信息是否比输入长度更有用？ |
| `aged-remaining` | `w >= τ` 的请求按 `a` 优先，其余按 `(R, a)` | 小；增加实际时间老化 | 限制长期被越过的情况，需要牺牲多少短请求收益？ |
| `aged-cost` | 同样的超阈值提升，其余按 `(T_hat, a)` | 中；增加小型标定与估计器 | token 数之外的执行成本信息是否值得加入？ |
| `aged-lpm`，可选 | 超阈值者按 `a`，其他按 `(-H, a)` | 小 | 收益主要来自 aging，还是来自剩余成本排序？ |
| `hrrn-time`，可选 | `1 + w / max(T_hat, ε)` 降序，以 `a` 打破平局 | 小至中；依赖时间口径 | 连续时间老化与原生 token 老化如何取舍？ |

`short-remaining` 允许长请求被持续越过，它的价值是消融参照。`aged-lpm` 只在需要分离 aging 效果时增加。`hrrn-time` 是经典 HRRN 的时间版本，不能包装成新的调度算法。

### 如何让成本估计确实增加信息

直接令 `T_hat = R / 固定吞吐` 不改变按 `R` 排序的结果，不能单列为一种有新能力的策略。

对普通因果全注意力模型，可从下面这个项目假设开始做小型标定：

```text
T_hat = β0 + β1 × R + β2 × [H × R + R × (R + 1) / 2]
```

`β1` 表示新 token 的近似线性计算开销；方括号表示新 query 访问已有前缀与新 token 的注意力工作量代理。这是待验证的成本模型，不是 SGLang 的耗时公式，也不声称跨模型、跨 GPU 通用。

在固定模型、精度、注意力后端和分块设置下，选少量不同的 `H`、`R` 组合测 prefill GPU 时间，再拟合非负系数或建立小型二维查表。用独立组合检验预测排序是否比只看 `R` 更准确。先固定模型再做最终比较，避免用最终测试结果不断调公式。

连续批处理下，请求实际耗时还依赖批次组合和并行 decode；分块又改变完成 prefill 的路径。第一版只把 `T_hat` 用作请求级排序代理。如果标定没有带来稳定收益，就保留 `aged-remaining` 作为最终方案，并解释原因。

### 如何限制候选，又保留老化语义

第一版有界变体采用明确规则：

1. 扫描整个等待队列，找出全部 `w >= τ` 的请求，按首次入队顺序放在最前面；这些请求不需要为了排序额外估计成本。
2. 在其余请求中选择首次到达最早的 `K` 个作为普通候选，只对这部分进行新增的成本评估。
3. 将普通候选按所选策略排序，接在超阈值请求之后。
4. 其他请求接在尾部，保留它们本轮扫描时的相对顺序。最终是否能进批仍由原生流程决定。

选择最早 `K` 个可以用 `heapq.nsmallest`。不能直接取已经被上一轮改排过的队列前 `K` 项，并把它们称为最早到达者。到达次序用明确的入队序号打破同一时刻的平局。

这只限制普通候选的额外评估数量。令总队列为 `N`、超阈值请求为 `M`，该设计仍包含约 `O(N log K + M log M + K log K)` 的选择和排序，以及队列重建、至多 `K` 次额外匹配；匹配成本还随输入长度变化。它不提供整个调度循环的常数时间保证。

实现时还需检查 `waiting_queue_prefix_matched()` 与负载统计消费者：部分匹配不能被报告成整队列都已匹配，队尾不能沿用过期命中值。原有统计或准入流程如果仍匹配更多请求，应保留并计入总开销。[匹配状态接口][src-policy]

先在候选覆盖全队列的情况下比较排序规则，再在长队列场景比较 `K = 32、64、128`。在相同 `K`、相同老化阈值下做消融，才能区分排序规则和候选限制各自的影响。

## 7. 实验应怎样安排

### 先固定条件，再增加变量

服务器已确定为单卡 A6000，驱动 `580.173.02`、CUDA `12.9`。第一阶段采用 `TP=1` 和普通全注意力文本模型；模型与启动参数起点见[项目设计](project-design.md)。实际可用显存、CPU、Linux/Python 环境、PyTorch 和 SGLang 安装组合仍需在服务器准备阶段记录，不预设实测吞吐。

比较时固定模型与 tokenizer、精度、KV 缓存容量、注意力后端、分块大小、批次 token 预算、运行请求上限、overlap 设置、输入轨迹和生成配置。业务优先级、HiCache、PD 分离和投机解码先不启用。优先保留固定且开启的分块 prefill，再选择一个代表负载改变分块大小，观察结论是否依赖这个设置。

生成长度第一轮可采用相同输出上限与明确的 EOS 处理，让 prefill 差异更容易解释；同时记录实际输出长度。另一轮使用不同输出长度检查 decode 干扰。新请求的 `R` 依据输入计算；若出现已生成输出后回退的请求，改用本轮需要重算的完整输入范围，并按本轮入队时间老化，首次等待统计不重写。回退次数随结果报告。

### 负载覆盖

下面是可缩放的设计起点，长度均为 token 数，最终要适配模型上下文和服务器容量。

| 负载 | 构造方式 | 主要检验点 |
| --- | --- | --- |
| 低复用、长短混合 | 短输入约 256～2K，长输入约 8K～16K，以短请求为多数 | 短输入优先与剩余量优先在低命中时是否接近 |
| 命中量与剩余量冲突 | 混合本文 A/B 类型请求，先用相同前缀完成缓存预热 | LPM 与剩余工作量排序的目标差异 |
| 热门前缀聚集 | 少数热门前缀组加独立前缀；分别运行冷缓存和统一预热条件 | DFS、LPM 的复用收益以及新策略的代价 |
| 长请求持续被短请求包围 | 持续注入短请求，同时穿插固定数量长请求 | aging 的收益、超阈值比例与最大观测等待 |
| 突发到达、较多 decode | 改变到达节奏与输出长度，观察实际队列跨过 128 | 原生回退、候选限制、token 老化与实际时间的差异 |

“低复用”不等于强行禁用 radix cache。关闭缓存会让原生缓存感知策略回退，不能把这种运行当作其正常实现。

每轮先完成相同的引擎预热，再建立该负载约定的初始缓存状态。冷缓存实验在预热后清空请求缓存；热缓存实验在清空后重放同一前缀预热集，并等其完成。正式运行期间的命中变化是策略结果，不能人为固定各请求的命中长度。

负载按预定到达时刻发送，保存输入与到达轨迹副本；不同策略使用同一轨迹。每种负载先用 FCFS 测出大致可持续速率，再选固定的低负载和排队明显的到达率供所有策略比较，不能对每个策略各自调一个更有利的请求率。

如果客户端并发上限使请求滞留在客户端，服务端实际看到的负载已经改变。记录计划发送、实际发送及服务端入队时刻，用同一机器内部的时间差统计各阶段；不要把两台机器未经同步的绝对时间直接相减。

### 控制实验数量

| 阶段 | 比较范围 | 产出 |
| --- | --- | --- |
| 机制筛选 | 四个核心原生策略 + 前三个候选；先选两个诊断负载、一个排队速率 | 约 14 次探索运行，只判断机制和可观察性 |
| 主结果 | 四个核心原生策略 + 最终候选；两个代表负载、两个固定请求率、至少三次独立重复 | 约 60 次主比较，展示每轮波动 |
| 针对性消融 | `short-input` 对 `short-remaining`；有无 aging；`R` 对 `T_hat`；全队列对有界候选 | 每次只改变一个因素，不遍历所有参数组合 |
| 补充解释 | 有需要时加入 `lof`、`random`、`aged-lpm`、`hrrn-time` 或路由键负载 | 解释主结果中的具体疑问 |

这是预算建议，单轮请求量和时长由服务器能力确定。主结果应有足够的短请求样本支撑尾部分位数；例如每轮约 2000 个短请求的最高 1% 也只有约 20 个样本。资源不足时展示实际样本数和轮间差异，不能把几百条请求的单次 P99 当作稳定结论。

`τ` 先依据 FCFS 实测等待分布选少量固定秒值，在正式比较前确定。`K` 先测 32、64、128 三档。只在代表负载上调参，再拿其他负载检验，避免把调参结果直接当作普遍优势。

## 8. 指标和记录方式

| 指标 | 本项目统计口径 | 需要解释的边界 |
| --- | --- | --- |
| 短请求 P95/P99 TTFT | 流式请求从客户端实际发出到收到首个生成 token；按固定的原始输入长度分组 | 不包含尚未实际发送的客户端等待；另行记录该部分 |
| 长请求最大等待 | 首次入队到首次准入的最大值，同时给长请求 P95/P99 与超过 `τ` 的比例 | 排队提升不是最大等待保证；准入也不是 GPU 已启动 |
| 总吞吐 | 完成请求数/秒、实际输出 token/秒，另报输入 token/秒 | 所有策略使用相同窗口；输入 token 吞吐包含缓存复用，不代表全是新算的 token |
| 缓存命中率 | 同一请求集合的实际可复用前缀 token 总数除以输入 token 总数 | 主实验只使用设备缓存；多层缓存需分层报告 |
| 匹配与排序开销 | 候选选择、前缀匹配、成本估计、排序、整个调度调用分别计时 | 分别给每调用分布及每完成请求摊销，避免调用次数变化掩盖成本 |
| decode 影响 | 输出长度分布、TPOT 或 ITL 的尾部指标 | TTFT 改善可能伴随 decode 变慢 |
| 完成情况 | 已发送、成功、失败、取消、结束时未完成数量及回退次数 | 分位数通常只来自成功请求，其他请求必须单独报告 |

短长分组在运行前固定。例如将输入不超过 2K 的请求定义为短请求，至少 8K 定义为长请求，中间组单独统计；不能按各策略的实际命中结果重新选“短请求”。可额外按剩余 token 分桶分析机制，但不替换主分组。

对测量结束时还没有首次准入的长请求，列出数量和截至当时的等待下界。让请求在停止注入后继续排空，或明确说明观察截止；不能只统计已完成请求，然后宣称最大等待变小。吞吐同时注明是否包含排空时间。

### 尽量复用现有测量入口

当前源码的主入口是 `python -m sglang.benchmark.serving`；`python -m sglang.bench_serving` 仍保留兼容入口，但已经弃用。[兼容入口][src-bench-compat]

基准工具已有 `--output-details`、`--cache-report` 和请求率等选项，可获得请求级 TTFT、输入输出长度、错误和缓存明细。复用这些产物，再补充本项目缺少的服务端首次排队记录、调度计时和轨迹关联信息。[基准实现][src-bench]

初步探索可用官方随机输入或共享前缀数据集；要精确重放 A/B 混合与固定到达轨迹时，再增加一个小型负载生成或回放脚本。服务端首次排队时间和排序 CPU 开销不能仅凭客户端 TTFT 反推。

### CPU 时间不要测错

在相同调用边界记录 `perf_counter_ns()` 的经过时间；需要严格区分 CPU 消耗时，再记录 `thread_time_ns()`。两者分别表示墙上经过时间与当前线程实际使用的 CPU 时间，不能混作同一个指标。

前缀匹配可能在排序阶段和准入阶段发生。分别记录两处次数、耗时、候选数量与队列长度；对使用临时树处理队内共享的策略，也把这部分归入匹配开销。统计总体调用时间时不要重复累加嵌套计时。

热路径采用内存计数和分布汇总，结束后导出；逐请求同步写日志或频繁同步 GPU 会改变被测系统。标定 GPU 成本使用设备侧事件或 profiler 的独立运行，不能用一次异步 Python 调用的返回时间代表 GPU 耗时。计时方式对所有策略保持一致。

### 支撑面试的三类图

1. 短请求 TTFT 分布或尾部分位图，旁边标明样本数、负载和重复轮次。
2. 不同 `τ` 下短请求 P99、长请求最大等待与吞吐的取舍图。
3. 不同队列长度、不同 `K` 下的匹配、排序和整体调度时间图，并标出原生 128 回退边界。

缓存命中率和吞吐放在同一结果表中辅助解释。即使候选策略只在部分负载获益，也保留其他负载和失败尝试，形成适用范围明确的结论。

## 9. 离线服务器如何推进

| 步骤 | 执行位置 | 必要产物 |
| --- | --- | --- |
| 确定环境 | Linux 登录设备通过 `ssh` 读取服务器信息 | GPU、显存、CPU、驱动、Python 和现有推理环境记录 |
| 准备文件 | Windows 编写项目；Linux 登录设备下载 | 对应上游源码、项目修改、模型与 tokenizer、本轮输入、适配服务器的依赖包 |
| 传入运行 | Linux 登录设备传文件到服务器 | 在服务器本地安装和运行所需文件，包括实际依赖需要的预编译包或缓存 |
| 实验 | 远程实验服务器 | 本地 Git 记录、请求记录、服务日志、指标汇总 |
| 回传分析 | 服务器传到 Linux 登录设备，再提供 Windows 分析副本 | 对应运行的输入副本、结果和图表 |
| 发布 | Linux 登录设备上的 GitHub 网页 | 操作者手动上传并提交支持性文件 |

下载和安装步骤按实际 GPU、Python 和 CUDA 环境编写，不能把联网 `pip install` 放进服务器流程作为默认前提。当前 Windows 环境承担代码、文档和分析，真实性能测量在远程服务器完成。

每轮只需保存能说明实验的材料：运行条件、策略与参数、输入和到达轨迹副本、请求级结果、服务日志、统计表及对应代码修改。可用一个运行目录和可读配置文件组织，不额外建设产物哈希、审批门禁或发布流水线。服务器与 Linux 登录设备都不执行 GitHub 推送；网页发布不影响先做实验。

## 10. 如何形成面试交付

简历一句话在实验结束后填写：

> 在［GPU、模型与负载］上实现并评估 SGLang 剩余 prefill 成本与等待老化调度，对比 FCFS、LPM、DFS-weight、HRRN；短请求 P99 TTFT 变化［实测值］，长请求等待和吞吐代价为［实测值］，并分析调度 CPU 开销。

讲解顺序建议为：A/B 请求解释动机 → 原生 HRRN 确定已有工作 → 修改排序与复用缓存的实现边界 → 负载与指标口径 → 收益、代价和适用范围。

能够答辩的问题包括：为什么不用纯输入长度；为什么 `R/固定吞吐` 没有新信息；原生 HRRN 已经做了什么；为什么到队首也可能无法准入；分块如何影响 TTFT；有界候选有没有漏掉久等请求；怎样确认 P99 不是样本或未完成请求造成的假象；吞吐下降时是否仍值得采用。

如果最终没有稳定胜过原生 HRRN，也可以用准确的负结果展示源码理解、实验设计和性能分析能力。现在不填写任何预期加速百分比。

GPU 型号与数量、驱动和 CUDA 已由用户补充。服务器准备阶段继续记录实际可用显存、CPU、Linux/Python 环境、现有依赖和模型、可用磁盘及实验时间预算；这些信息不阻碍本次设计文档与实现计划的编写。
