## 2. M1：服务器记录与离线基线

### 工作内容

通过 Linux 登录设备记录服务器实际 GPU 名称、可用显存、CPU、内存、Linux 发行版与架构、Python 版本、现有环境和可用磁盘。驱动与 CUDA 按用户提供值保留，同时分别记录 `nvidia-smi`、`nvcc --version` 和已有 PyTorch 的 `torch.version.cuda`，注明缺失项，不从其中一个值推断其余两个。

以 RTX A6000、`TP=1`、Qwen2.5-7B-Instruct、BF16 为默认设计。优先使用兼容的现有环境；需要新建环境时准备 Python 3.11 的独立环境，不改系统驱动。若服务器已经有可用的同类模型，先记录名称与配置，再决定是否沿用并同步修改模型相关实验参数。

在 Linux 登录设备准备以下文件：

- 上游固定提交的源码及本项目文件，完整模型权重、tokenizer 和模型配置。
- 对应服务器 Python ABI、Linux 平台和 CUDA 12.9 路径的依赖包，包括实际后端需要的二进制包、构建工具或 JIT 资源。
- 实验脚本使用的少量 Python 依赖。优先复用 SGLang 环境中的包，不另建庞大的分析工具链。

不要只执行一次普通 `pip download sglang` 就假定所有平台包、构建依赖和 JIT 资源都已经准备好。对照固定版本安装说明选择包组合，在目标环境进行实际安装；安装过程的具体命令与包版本保存到环境文档。

在服务器建立上游工作副本并使用本地 Git 记录基线。如果取得的是不含 Git 历史的源码压缩包，可以在解压目录初始化本地仓库；上游提交仍写在说明文件中，不把本地初始提交当作上游版本号。

按设计中的启动值运行 FCFS，完成一组覆盖短输入、长输入和已有前缀复用的实际请求。记录解析后的后端、精度、KV 容量和运行请求上限。这组数据同时用于了解容量与计时范围，不另外建立启动冒烟套件。

### 交付物

| 文件 | 内容 |
| --- | --- |
| `docs/environment.md` | 服务器实况、实际安装命令、包版本、本地模型路径和已观察到的问题 |
| `configs/a6000.json` | 全部策略共用的服务器参数起点和实际调整值 |
| `patches/upstream-base.txt` | 上游仓库、源码提交与来源说明 |
| 首轮运行目录 | FCFS 服务日志和原始请求结果 |

完成条件是服务器能在无外网条件下加载选定模型、完成所选输入，并留下实际参数和结果。只有真实安装或运行问题才触发替代包、后端或源码版本的调整；调整后相关策略共用同一环境。

## 3. M2：先让基线可测、结果可关联

### 工作内容

实现 `generate_workload.py` 和 `replay.py`。先支持两种轨迹：`prefix-conflict`、`long-wait`；输出固定 token IDs、计划到达偏移、原始输入组别、生成参数和固定 `rid`。预热前缀与正式请求分开保存，正式请求使用变化的后缀。

回放客户端运行在服务器回环接口上，按轨迹异步发送，保存实际发送延迟与流式结果。识别首个生成事件，记录错误和未完成请求。采用相同请求率时，不能因为客户端在等待前一个请求而把持续到达变成串行调用。

补充服务端测量：

1. 在普通请求入队路径保存本轮序号；测量收集器在第一次入队时保存首次时间。
2. 在请求首次进入 `can_run_list` 的相应批次构建位置记录首次准入；重复分块和请求回退不覆盖它。
3. 在 `calc_priority()` 的分项以及 `_get_new_batch_prefill_raw()` 的整体边界计时，分开记录评分匹配与准入匹配。
4. 保存配置策略、实际策略、队列长度及两类回退计数。
5. 接入 scheduler 实际的正常关闭路径，在进程被结束前导出内存记录；`run_case.py` 使用相应的正常结束方式收集产物，不能假定强制结束后还能读取内存。

实现 `run_case.py` 的单次运行流程和 `analyze.py` 的初版：读取一个案例配置，启动本轮服务，预热或清缓存，回放，排空，正常结束自己启动的服务，按 `run_id + rid` 合并结果。

先运行 FCFS，再运行 LPM、DFS-weight、HRRN，原生调度分支不改变。用相同的记录方式做一次有记录／无记录的 FCFS 对照，确认采集代价是否已经足以影响分析；若影响明显，则简化记录后再开始主比较。

### 验证与完成条件

人工构造少量结果记录，核对首次等待、TTFT、分位数、吞吐和 token 加权命中率；加入一个未准入请求和一个失败请求，确认不会被静默视为零延迟或成功请求。

在实际服务器请求中，能够关联客户端结果、首次排队等待和相应运行配置；正常结束能拿到服务端测量文件。得到四个原生策略的可读结果，能从记录判断 LPM／HRRN 是否发生策略回退。

主要产物为 `experiments/` 中的四个初版脚本、测量补丁、完整运行目录和初版 `summary.json`。这一步完成后，即使尚无新策略，仓库也已经能提供真实基线证据。

## 4. M3：实现三个主要的简单策略

### 实现顺序

| 顺序 | 修改 | 可检查结果 |
| --- | --- | --- |
| 1 | `short-input`：读取原始输入长度，按入队序号打破平局 | 展示输入长度排序与 FCFS 的差别 |
| 2 | `short-remaining`：使用引擎真实匹配和有效前缀上限计算 `R` | 同输入长度、不同命中时能够给出不同次序 |
| 3 | `aged-remaining`：单次读时钟，先提升超阈值请求，再按 `R` 排序 | 久等长请求能够越过新到短请求 |

新增分支位于通用全队列匹配之前，原生策略仍走其原有路径。先只支持全队列候选；新分支的负载查询匹配状态按设计使用既有估计分支。

新增 CLI 选项、入队序号和成本特征的提取随实际需求一起接入。纯排序部分尽量只依赖 Python 标准库，便于 Windows 做局部验证；不为此构造完整的假 SGLang 运行时。

### 必要验证

- 等长、等剩余量和同一时间到达时，入队次序稳定，请求集合不丢失或重复。
- 阈值边界按 `>=` 生效；刚入队的短请求不会越过已经超阈值的请求。
- 真实命中与有效前缀上限一致，完全相同输入不会被错误视为可跳过全部引擎处理。
- 请求回退时采用本轮长度和本轮排队时间；首次排队等待统计保留原始值。

只为这些会影响请求处理与实验含义的边界编写少量测试。代码完成后在服务器复用 M2 的两条轨迹验证实际服务，检查输出、状态和缓存记录；不要求重排批次后的输出逐字节一致。

完成条件是三个标识可通过真实 SGLang 服务选择、每种策略有可核对的请求顺序与完整 GPU 运行记录。导出 `patches/scheduler.patch`，让支持性仓库可以审查实际改动。

## 5. M4：第一轮机制比较

用四个原生策略与前三个候选，在 `prefix-conflict`、`long-wait` 各运行一个排队明显的到达率，约 14 次探索案例。每例先使用数百个请求确定运行时间与现象，探索样本不用于发布稳定的 P99 结论。

检查三个问题：

1. `short-input` 与 `short-remaining` 是否在同输入不同命中组中产生预期的排序差异；差异是否反映在 TTFT 上。
2. `aged-remaining` 对长请求首次等待有什么影响，代价体现在哪些短请求、吞吐或命中率上。
3. LPM／HRRN 有多少调用已经回退，调度时间主要花在匹配、排序还是批次构建。

补充 `mixed-low-reuse` 或 `hot-prefix` 时，由上述结果中的具体疑问驱动。固定主比较将使用的两类负载，避免观察最终结果后只保留对候选最有利的负载。

交付探索结果表、至少一张初版图和一段解释；记录哪些现象已经得到支持，哪些仍未观察到。负结果不构成实现失败。

## 6. M5：有界候选

### 工作内容

实现 `K=0` 表示全队列，以及 `K=32／64／128` 的候选范围。所有超阈值请求仍来自全队列扫描；普通候选依据本轮入队序号选择，未入选尾部保留本轮扫描顺序。

评分匹配只服务于普通候选，超阈值和队尾请求仍在原生准入路径中匹配。新策略的匹配状态不能让负载查询读取尚未刷新过的队尾匹配值。

### 验证与实验

构造一个上一轮已经改排、最老请求位于队尾的队列，检验候选选择使用入队序号而不是列表位置。再让该请求超过阈值，检验它在任意 `K` 下都会进入提升集合。

在可观察到不同队列长度的同一负载上比较全队列与三档 `K`，绘制匹配、排序、整个调度调用和批次构建耗时。既看每调用时间，也看每完成请求摊销；同时报告 TTFT、等待和吞吐。

完成条件是评分匹配次数确实受候选数约束，并能解释其他匹配调用仍来自哪里。只有评分部分变快、整体未变快时，如实记录，不把局部下降写成整个调度 CPU 优化。

## 7. M6：GPU 标定与 `aged-cost`

### 工作内容

实现 `calibrate.py`，采用设计中的 16 组目标 `H/R`、少量预热和每组约 20 个计时样本。被测请求独占批次，输出设为 1 token，用 worker 中的设备计时累计其 prefill 各块耗时。

每个样本使用新后缀，或在计时区间外恢复目标缓存状态，避免重复输入被前一轮完全缓存。记录实际 `H/R`、分块数和设备耗时，不拿客户端 TTFT 当作标定标签。

按目标组合划分拟合与保留数据，拟合三项非负模型，保存系数与单位，比较对保留组合的排序能力。实现 `aged-cost` 在启动时读取模型，运行时仅计算标量分数。

### 验证与实验

检查 JSON 的单位和加载结果能够重现离线评分；路径不存在或内容不能解释时给出直接错误，不能默默换用另一个策略。

先在两个探索负载上使用相同 `τ`、相同 `K` 比较 `aged-cost` 与 `aged-remaining`，再判断是否值得作为最终候选。二者的区别只有成本估计器，不能同时换分块或请求率。

交付标定原始数据、系数文件、保留组分析与在线对照。即使成本模型没有稳定收益，也完成 `aged-cost` 的实现与比较，形成“为什么简单代理已经足够”或“为什么批次效应盖过单请求估计”的解释。

## 8. M7：正式比较与消融

### 正式运行前确定的内容

根据独立探索结果确定最终候选、`τ`、`K`、两个代表负载、两个固定到达率、生成参数与三组轨迹种子。这些配置写进可读文件；不增加参数审批、配置契约或哈希检查。

最终候选的选择综合短请求 P99、长请求等待、吞吐、缓存命中率与 CPU 成本；不捏造一个加权总分掩盖取舍，也不要求它必须胜过所有原生策略。若没有整体优势，仍可以把最有解释价值的候选放入主表。

### 主比较

四个原生策略加一个最终候选，两个负载、两个到达率、三次独立重复，共约 60 次。每个种子对应的轨迹被全部策略复用，策略运行顺序在不同种子间轮换，降低执行次序与机器状态的影响。

主轮起点可以是每例约 2500 个请求，80% 短请求时约有 2000 个短请求；先依据单次实际时长决定样本预算。按原始长度报告组内样本数及每轮分位数。压力负载至少有一次明确跨过 128，另保留一个大部分调度调用不超过 128 的场景。

### 针对性消融

| 对照 | 固定项 | 解释内容 |
| --- | --- | --- |
| `short-input` 与 `short-remaining` | 输入、请求率、生成参数、候选范围 | 缓存信息的价值 |
| `short-remaining` 与 `aged-remaining` | 剩余量估计、候选范围 | aging 的收益和代价 |
| `aged-remaining` 与 `aged-cost` | `τ`、`K`、服务参数 | 耗时估计器的价值 |
| 同策略的全队列与三档 `K` | 排序规则与 `τ` | CPU 开销与候选覆盖范围的取舍 |
| 同 aging 策略的三档 `τ` | `K`、负载、请求率 | 短请求尾延迟与长请求等待的取舍 |
| 分块 2048 与 4096 | 模型及其余服务配置 | 结论对分块设置的依赖 |

消融在代表负载上运行，不做所有维度的笛卡尔积。上述对照中没有进入主表的候选仍保留自己的原始结果。

`aged-lpm` 只在需要进一步分离缓存聚集与 aging 时实现，并保留原生 LPM 的队内共享处理；`hrrn-time` 只在 token 老化与实际时间的差别仍需直接检验时实现。`lof`、`random` 可作低成本补充；`routing-key` 需要专门的路由键负载，不强行加入无对应语义的主比较。

### 单卡预算

GPU 总时间按实际测到的“服务启动 + 预热 + 请求注入 + 排空”逐轮估算，再加独立标定运行。不要把 `请求数／请求率` 当作包含全部阶段的总运行时间。

如果预算不足，先完成一个代表负载的 30 次主比较，再补第二个负载；减少可选策略和重复参数组合，保留四个核心基线、三次重复和已有负结果。当前没有用户给出的总时长，因此不承诺具体完成日期。

完成条件是原始产物能够支撑主表，未完成与失败请求有明确统计，策略回退与请求回退可分别解释，结论只覆盖实际运行过的模型、GPU 和负载。

## 10. 每阶段如何保留进展

在 Windows 工作区记录文档、补丁和分析文件的变更；在服务器上记录实际运行的上游源码修改。每个有完整含义的阶段形成一个清楚的本地 Git 提交，例如“实现剩余 token 排序与请求等待记录”。不需要把这些提交推送到 GitHub 才能继续。

每轮运行保存输入副本、配置和请求结果；阶段结论记录已经观察到的现象与剩余问题。遇到性能没有改善时，先根据计时分解和请求群体分析原因，再决定增加哪个已列出的消融，不继续无目的堆策略。
